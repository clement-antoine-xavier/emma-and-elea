# Emma & Elea

Next.js 16 App Router app with Astryx UI, Prisma ORM 7, and Better Auth.

## Stack

- Next.js 16.4.3 + React 19.3 + TypeScript
- Astryx 0.7.4 (Butter theme) + Recharts 3.10 for the dashboard charts
- Prisma ORM 7.10.1 + PostgreSQL 18 (Prisma Postgres on Vercel)
- Better Auth 1.7.14 (email/password, admin, organization, MCP OAuth)
- Vercel AI SDK 7 + AI Gateway for the in-app assistants
- next-intl 4.14.9 (English and French, locale from the `NEXT_LOCALE` cookie)
- Zod 4 + React Hook Form 7 for forms

Architecture decisions are recorded in [`docs/adr/`](docs/adr/README.md) using MADR.

## Prerequisites

- Node.js 24+ (CI and the Docker image currently use Node 26; Vercel uses Node 24)
- Docker + Docker Compose

## Local setup

```bash
npm install
cp .env.example .env
```

Generate an auth secret and put it in `.env`:

```bash
openssl rand -base64 32
```

Start PostgreSQL and apply migrations:

```bash
docker compose up -d --wait postgres
npm run db:migrate
```

Run the app:

```bash
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). The UI language comes from
the `NEXT_LOCALE` cookie (English by default; use the language switcher to change
it), and accounts are created at `/sign-up`. Onboarding asks for the business
name and its first site. `/dashboard/settings` manages the organization values,
sites, labour rates, energy tariffs and equipment. `/dashboard/catalog` manages
items, categories and allergen declarations. `/dashboard/purchasing` manages
suppliers and goods receipts; posting one creates its lots and stock movements,
visible under `/dashboard/stock`. `/dashboard/recipes` manages versioned
recipes, live cost previews and stored snapshots; publishing requires every
price, rate and tariff to resolve. `/dashboard/production` plans and completes
batches, allocates lots FEFO, records waste and exposes lot traceability.

## Environment

`.env` is ignored by git. See `.env.example` for the required keys:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Direct PostgreSQL/Prisma Postgres connection string used by migrations |
| `DATABASE_URL_POOLED` | Pooled Prisma Postgres URL used by the app at runtime (set by the Vercel integration) |
| `PRISMA_DATABASE_URL` | Optional fallback for the pooled URL |
| `DIRECT_URL` | Optional migration endpoint override for other hosts |
| `BETTER_AUTH_SECRET` | Signing/encryption secret (32+ bytes) |
| `BETTER_AUTH_URL` | Public app URL used by Better Auth |
| `MCP_RESOURCE_URL` | Public URL of the MCP endpoint (defaults to `$BETTER_AUTH_URL/mcp`) |
| `API_RESOURCE_URL` | Public base URL of the REST API (defaults to `$BETTER_AUTH_URL/api`) |
| `AI_GATEWAY_API_KEY` | Server-only AI Gateway key; optional on Vercel where OIDC is used |
| `ASSISTANT_ENABLED` | Set to `true` to show Emma and Éléa in the dashboard |
| `ASSISTANT_MODEL` | AI Gateway model id, for example `openai/gpt-5.4` |
| `ASSISTANT_EMMA_MODEL` / `ASSISTANT_ELEA_MODEL` | Optional per-persona Gateway model overrides |
| `TOOL_APPROVAL_SECRET` | Signs human approval requests; required in production |
| `ASSISTANT_TELEMETRY_ENABLED` | Set to `true` to opt into AI SDK telemetry (defaults to false) |
| `ASSISTANT_MAX_TURNS` / `ASSISTANT_DAILY_TOKEN_BUDGET` | Guardrails for a run |
| `ASSISTANT_RETENTION_DAYS` | Conversation retention window (defaults to 30) |
| `BLOB_READ_WRITE_TOKEN` | Local Vercel Blob read-write token |
| `BLOB_STORE_ID` | Vercel Blob store id (paired with OIDC on Vercel) |

Real values belong in `.env` (gitignored). `.env.example` contains placeholders
only; never put a real key in a committed file, a Docker build argument or a
workflow.

Inside Docker, Compose overrides `DATABASE_URL` to use the `postgres` service hostname.

## Database

```bash
docker compose up -d --wait postgres   # start the local Postgres container
docker compose down              # stop it
npm run db:migrate               # create and apply a migration
npm run db:generate              # regenerate the Prisma client
npm run db:seed                  # add demo catalogue data (see below)
npm run db:prune-assistant       # expire stale approvals and old assistant chats
npm run db:studio                # open Prisma Studio
```

The Prisma client is generated into `src/generated/prisma` (gitignored). It is regenerated by `npm run dev`, `npm run build`, and `npm install`.

### Seed data

`npm run db:seed` adds a demo site, catalogue, supplier prices, equipment, rates and one draft croissant recipe to an organization. It is idempotent and does not overwrite values you edited by hand. With several organizations, choose one explicitly:

```bash
npm run db:seed -- --org=my-bakery
```

The command exits with instructions when no organization exists yet; create one at `/sign-up` first. Units and allergens are seeded by the database migration, not by this script.

Organizations created before onboarding asked for a first site can get one with:

```bash
npm run db:backfill-sites
```

## OAuth resources: MCP and REST API

Better Auth is the authorization server and both surfaces are protected
resources with separate audiences (ADR-0020, ADR-0021):

| Surface | Resource | Token audience |
| --- | --- | --- |
| MCP | `POST /mcp` | `$BETTER_AUTH_URL/mcp` |
| REST API | `/api/...` | `$BETTER_AUTH_URL/api` |

A token issued for one resource is rejected by the other. Both use the same
resource-neutral scopes (`api:read`, `api:write`, `api:execute`, `api:finance`)
and the same tenant claim, so consent is understood the same way everywhere.

### MCP

- Route: `src/app/mcp/route.ts` (POST only, stateless 2026-07-28 transport)
- Authorization: `src/server/mcp/handler.ts` (`requireMcpAuth` + JWKS)
- Tools: `src/server/mcp/tools/*` — thin wrappers over the services
- Consent screen: `/consent`

```text
http://localhost:3000/mcp
```

The host discovers the authorization server from the `401` challenge, registers
itself (DCR or CIMD), opens `/sign-in` then `/consent`, and stores the token. The
token is bound to the organization that was active at consent time and can never
grant more than the member's current role.

### REST API

- Entry points: `src/app/api/**/route.ts`
- Token verification: `src/server/api/token-auth.ts` (`401` with RFC 9728
  metadata, `403 insufficient_scope`)
- Error mapping: `src/server/api/respond.ts`

Read endpoints:

```text
GET /api/me
GET /api/sites                    GET /api/sites/:id
GET /api/catalog/items            GET /api/catalog/items/:id
GET /api/catalog/categories
GET /api/customers                GET /api/customers/:id
GET /api/stock/levels             GET /api/stock/lots        GET /api/stock/lots/:id
GET /api/production/batches       GET /api/production/batches/:id
GET /api/orders                   GET /api/orders/:id
GET /api/dispatches               GET /api/dispatches/:id
GET /api/reports                  (requires api:finance)
```

Writes (`api:write`) currently cover the catalog and customers:

```text
POST  /api/customers                        PATCH /api/customers/:id
POST  /api/customers/:id/archive
POST  /api/catalog/items                    PATCH /api/catalog/items/:id
POST  /api/catalog/items/:id/archive
POST  /api/catalog/categories               POST  /api/catalog/categories/:id/archive
```

Selecting, ordering and posting ledger movements stay on the Server Actions until
the remaining write endpoints land.

Send `Authorization: Bearer <access_token>`. Server Components and Server
Actions keep using the session cookie; only these resource routes accept bearer
tokens.

### Discovery

```text
/api/auth/.well-known/oauth-authorization-server
/.well-known/oauth-authorization-server/api/auth
/api/auth/jwks
/.well-known/oauth-protected-resource
/.well-known/oauth-protected-resource/mcp
/.well-known/oauth-protected-resource/api
```

The protected-resource documents live on the app origin (RFC 9728), not under
`/api/auth`. Set `MCP_RESOURCE_URL` and `API_RESOURCE_URL` to the public HTTPS
URLs in production; they are the token audiences and must match what clients
call.

## In-app assistants

The dashboard exposes two assistants behind `ASSISTANT_ENABLED`:

- **Emma** — customers, orders, deliveries, daily sales and revenue.
- **Éléa** — production, planning, stock, purchasing, recipes/costs, reports and
  the team.

`/dashboard/assistant` is the zero state with persona selection and starter
prompts; a conversation lives at `/dashboard/assistant/<id>` with the transcript
and a resizable approval panel (a full-screen dialog on mobile). The dashboard
side nav links to the zero state.

They use the Vercel AI SDK with AI Gateway models. Tools call the same services
as the pages and Server Actions. The authenticated session actor supplies the
organization; no tool accepts an organization id. A capability is registered only
when the member holds every required permission, and the service still runs
`assertPermission`.

Drafts are created immediately. Posting a receipt, dispatch or stock count,
starting or completing a batch, publishing a recipe and deciding an absence
pause the run for an approval card. Approvals are signed with
`TOOL_APPROVAL_SECRET`, expire after ten minutes and are recorded in
`agent_approval`.

`POST /dashboard/assistant/stream` returns an AI SDK UI message stream consumed
by `useChat`. It is outside `/api/**` on purpose: it uses the session cookie, not
an OAuth bearer token. See
[ADR-0030](docs/adr/0030-replace-openai-agents-with-vercel-ai-sdk.md).



The backend is layered: entry point → service → repository → Prisma.

- `src/app/**`, `src/app/actions/**`: Server Components, Server Actions and Route Handlers. They resolve the actor, validate input, call one service, and map errors.
- `src/server/services/`: authorization, tenant rules and use cases.
- `src/server/repositories/`: every Prisma query and row-to-DTO mapping.
- `src/server/auth/`: session actor resolution, Better Auth gateway and role wiring.
- `src/server/validators/`: Zod schemas shared by Server Actions and forms.
- `src/server/domain/`: pure domain calculations and expected errors.

See [ADR-0012](docs/adr/0012-layer-the-backend.md) for the rules and the ESLint
boundaries. Multi-row postings (receipts, batch completion, dispatches) are
written by one repository transaction fed by a pure domain posting plan; see
[ADR-0014](docs/adr/0014-post-ledger-changes-in-one-transaction.md).

## Forms

All forms use Zod schemas in `src/server/validators/` with React Hook Form. The reusable Astryx field wrapper is `src/components/form-text-input.tsx`; server errors render in an Astryx `Banner`. Schemas receive a translator so validation messages follow the active locale.

## Internationalization

`next-intl` provides translations and formatting. URLs carry no locale prefix:
the active locale comes from the `NEXT_LOCALE` cookie written by the language
switcher (English when the cookie is missing or unknown).

- Routing: `src/i18n/routing.ts` — supported locales and the default locale
- Locale cookie: `src/i18n/locale.ts` — `NEXT_LOCALE` name, attributes, and fallback
- Request config: `src/i18n/request.ts` — reads `cookies()` and loads the catalog
- Locale switch: `src/app/actions/locale.actions.ts` — sets the cookie; the switcher refreshes the route
- Messages: `messages/en.json`, `messages/fr.json`
- Pages: `src/app/`

The cookie is request data, so every route renders per request; `src/app/layout.tsx`
sets `instant = false` to allow that under Cache Components. There is no Proxy and
no `Accept-Language` negotiation.

Add a language by extending `routing.locales` and adding `messages/<locale>.json`.
Both catalogs must share the same keys; `npm test` fails otherwise. French copy
is maintained in-repo and should be reviewed by a French speaker.

## Testing

```bash
npm test                  # Jest unit and component tests
npm run test:coverage     # Unit tests with the coverage report and thresholds
npm run test:integration  # Repository tests against the real PostgreSQL
npm run test:e2e          # Playwright E2E against PostgreSQL
```

Install the Playwright browser once:

```bash
npx playwright install chromium
```

Integration suites (`*.integration.test.ts`) create their own organization and
user with a random suffix, build fixtures through Prisma, and delete only those
rows. They never truncate the database, so they are safe against a development
database. Start PostgreSQL with `docker compose up -d postgres` and apply
migrations with `npm run db:deploy` before running them.

E2E tests use the `DATABASE_URL` from `.env`, run against the dev server at `http://localhost:3000`, create unique `e2e-*@example.com` users, verify them in PostgreSQL, and delete them afterward. The suite covers full feature flows plus catalog/settings editing and archiving, team edits, tenant isolation, signed-out redirects, 404s and the translated dashboard.

## Vercel

Vercel is the primary deployment target; the Docker path below remains supported.

1. Link the project and pull development secrets:

   ```bash
   vercel link
   vercel env pull
   ```

2. Add the Prisma Postgres integration from the Vercel Marketplace. It sets
   `DATABASE_URL` (direct, for migrations), `DATABASE_URL_POOLED` (runtime) and
   `POSTGRES_URL`. The app prefers `DATABASE_URL_POOLED`.
3. Create a public Blob store and connect it to the project. Vercel provides
   `BLOB_STORE_ID` and OIDC automatically.
4. Set `BETTER_AUTH_URL` to the production custom domain,
   `BETTER_AUTH_SECRET`, `TOOL_APPROVAL_SECRET`, and the assistant/Gateway values
   for Production. Preview deployments derive their origin from `VERCEL_URL`.
5. Deploy. `vercel.json` runs `npm run vercel-build`, which applies migrations
   only in Production. Preview deployments share the database unless you connect
   a separate Prisma Postgres resource to the Preview environment.

The assistant route exports `maxDuration = 300`; Vercel clamps it to the plan's
limit.

## Docker

Build and run the app, migrations, and PostgreSQL together:

```bash
docker compose up --build -d
```

Compose reads `.env` both for `${...}` interpolation and as the app service's
`env_file`, so every key documented above (including the assistant keys) reaches
the container without being duplicated in `docker-compose.yml`. The explicit
`environment` entries for `DATABASE_URL`, `BETTER_AUTH_URL` and the resource URLs
win over the file.

Compose starts three services on the `postgres-network` network:

- `postgres` — `postgres:18.6-alpine3.24`
- `migrate` — one-shot `prisma migrate deploy`
- `emma-and-elea` — Next.js standalone server on port `3000`

The app waits for the migration job to complete before starting. The Postgres 18 image stores data under `/var/lib/postgresql`, so the named volume is mounted there.

Stop the stack:

```bash
docker compose down
```

## CI

- `.github/workflows/next.js.yml` — starts a real PostgreSQL 18.6 service, applies migrations, then runs `npm run typecheck`, `npm run lint`, Jest, `npm run build`, and Playwright E2E on pushes and pull requests to `main`.
- `.github/workflows/docker.yml` — builds the Docker `runner` target and pushes `ghcr.io/clement-antoine-xavier/emma-and-elea` on pushes to `main` and tags matching `v*`.

Image tags are `main`, `latest`, `sha-<short>`, and semver tags from `v*` releases. Images target `linux/amd64`. The two workflows run independently; the Docker build runs `next build` but not ESLint. Third-party actions are pinned to exact release tags (`vX.Y.Z`); update them deliberately.

## Notes

- Prisma is pinned to 7.x. Prisma 8 RC uses a different ORM API that Better Auth's Prisma adapter does not support yet.
- The production image uses Next.js `output: "standalone"` outside Vercel and runs as the unprivileged `node` user.
- Profile images are public Vercel Blob objects; do not use this path for sensitive documents.
