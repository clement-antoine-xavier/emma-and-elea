## Backend architecture

Layered: entry point → service → repository → Prisma. See ADR-0012.

- Entry points (`src/app/**`, `src/app/actions/**`) resolve the actor, validate input, call one service, and map errors. No Prisma or `auth.api` imports.
- Services (`src/server/services/`) own authorization, tenant rules and orchestration. Return plain DTOs or throw `DomainError`.
- Repositories (`src/server/repositories/`) own every Prisma query. No business rules.
- Better Auth organization mutations go through `src/server/auth/better-auth.gateway.ts`; session and membership resolution through `src/server/auth/actor.ts`.
- Validators live in `src/server/validators/` and are client-safe (pure Zod).
- `src/lib/permissions.ts` is the shared role matrix; `src/server/domain/` holds pure domain calculators.
- ESLint forbids Prisma/Better Auth imports in `src/app/**` and server-layer imports in `src/components/**`.

## Astryx UI

Use Astryx before writing custom UI. Discover, then compose; don't hand-roll layout.

- Find: `npm run astryx -- search "<query>"`; read `component <Name>` before using it.
- Pages: `template <name> <path>`; keep the frame, gap, and padding; replace the content.
- Layout: no raw `<div>`/`<span>`; use `Stack`, `HStack`, `Card`, `Center`, `Grid`, `Section`.
- Styling: component props first, then tokens (`var(--color-*)`, `var(--spacing-*)`, `var(--radius-*)`). No raw hex/px.
- Dense data: `Table` or `List`/`Item` rows, not Card-wrapped lists. `Badge` is for counts.
- Theme: `themes[defaultThemeSlug]` is passed once in `src/app/providers.tsx`. Customize with `defineTheme({extends: butterTheme, ...})`.
- `theme eject` only when the user explicitly asks for an independent source fork.
- Do not run `astryx init`: it would recreate `GEMINI.md` and the generated Astryx block. This file is hand-maintained.
- Before delivery: `npm run astryx -- doctor --built <dir>`.

## Internationalization

`next-intl` 4.14.9 without locale-based routing. URLs carry no locale prefix.

- Routing config: `src/i18n/routing.ts` (`locales`, `defaultLocale`). Add a locale there and in `messages/`.
- Locale: `src/i18n/locale.ts` defines the `NEXT_LOCALE` cookie (`path=/`, one year, `lax`) and `resolveLocale`, which falls back to `en` for unknown values.
- Request config: `src/i18n/request.ts` reads `cookies()` and supplies the locale plus messages. There is no Proxy and no `[locale]` segment.
- Rendering: the cookie is request data, so every route is dynamic. `src/app/layout.tsx` sets `export const instant = false` to allow the block under `cacheComponents`; do not add `generateStaticParams` for locales.
- Switching: `setLocaleAction` in `src/app/actions/locale.actions.ts` writes the cookie; `LocaleSwitcher` calls it and then `router.refresh()`. The URL must not change.
- Messages: `messages/en.json` and `messages/fr.json`. A Jest test asserts both catalogs have the same key paths; add keys to both.
- Server Components: `getTranslations` from `next-intl/server`; Client Components: `useTranslations` from `next-intl`.
- Navigation: import `Link`, `useRouter`, and `usePathname` from `next/link` and `next/navigation`. There is no locale-aware navigation wrapper.
- Validation: schemas in `src/server/validators/` stay free of `next-intl`; `createAuthSchema(mode, t)` receives a translator function from the component.
- Pages live under `src/app/`; `src/app/layout.tsx` is the root layout.
- French copy is in-repo and unreviewed by a native speaker; treat edits to `messages/fr.json` as content changes.

## Forms

All data input uses Zod for validation and React Hook Form for state.

- Schemas: `src/server/validators/*.ts`; export inferred TypeScript types from them.
- Forms: `useForm` + `zodResolver`; wrap Astryx inputs with `Controller` (see `src/components/form-text-input.tsx`).
- Wrap fields in a real `<form onSubmit={handleSubmit(onSubmit)}>` and use Astryx `FormLayout` inside.
- Field errors map to Astryx `status={{type: 'error', message}}`; server errors use `setError('root', …)` and a `Banner`.
- Do not hand-roll `useState` validation for forms.
- Keep `@hookform/resolvers` on 5.x while Prisma 7 depends on `effect@3`; v6 declares an optional `effect@4` peer and breaks npm resolution.

## Testing

- Jest + React Testing Library for unit/component tests: `npm test` (or `npm run test:watch`).
- Playwright for E2E: `npm run test:e2e` (or `npm run test:e2e:ui`). Locally it uses the dev server; CI builds once and runs the standalone server with auth rate limiting disabled for the suite.
- E2E uses the real PostgreSQL at `DATABASE_URL`. `e2e/global-setup.ts` deletes stale `e2e-%@example.com` users; tests create unique users and delete them afterward.
- Keep the Playwright `baseURL` at `http://localhost:3000` to match `BETTER_AUTH_URL`.
- Astryx is ESM; mock `@astryxdesign/core/*` in Jest component tests instead of importing the real package.
- CI runs both suites in `.github/workflows/next.js.yml` against the PostgreSQL service.

## CI

- `.github/workflows/next.js.yml` starts a real PostgreSQL 18.6 service, runs `npm run db:deploy`, then runs `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, and Playwright E2E on pushes and pull requests to `main` with Node 26.12.1.
- `.github/workflows/docker.yml` builds the Docker `runner` target and pushes `ghcr.io/clement-antoine-xavier/emma-and-elea` on `main` and `v*` tags, with GHA layer cache, max provenance and an SBOM attestation.
- The workflows are independent; Docker does not wait for Next.js checks. The image is `linux/amd64` only, and the `migrator` target is not published.
- The Docker builder uses placeholder `DATABASE_URL` / `BETTER_AUTH_SECRET` values; CI uses a throwaway PostgreSQL service. Never put real secrets in workflow files.
- Third-party actions are pinned to exact release tags (`vX.Y.Z`). Update them deliberately after reviewing the release.

## Prisma

Prisma ORM **7.10.1** with PostgreSQL. Do not upgrade to Prisma 8 RC yet: its `@prisma/orm-postgres` contract API is not supported by Better Auth's Prisma adapter.

- Config: `prisma7.config.ts` (Prisma 7's filename; Prisma 8 reads `prisma.config.ts`).
- Schema: `prisma/schema.prisma`; migrations: `prisma/migrations/`.
- Client output: `src/generated/prisma` (gitignored, regenerated by `predev`/`prebuild`/`postinstall`).
- Runtime client: `src/lib/prisma.ts` via `PrismaPg` from `@prisma/adapter-pg`.
- `DATABASE_URL` lives in `.env`; `.env.example` documents the keys.
- Load the matching skill before schema, migration, client, or database work.

- Setup and connection: `prisma-orm-setup`.
- Database provisioning: `prisma-postgres-setup`.
- Client queries and CRUD: `prisma-client-api`.
- CLI and migrations: `prisma-cli`.
- Driver adapters: `prisma-driver-adapter-implementation`.
- v6 → v7: `prisma-upgrade-v7`; MongoDB upgrades: `prisma-mongodb-upgrade`; Prisma Compute: `prisma-compute`.
- Deprecated aliases: `prisma-database-setup`, `prisma-postgres`; use only when explicitly named.

## Better Auth

Better Auth **1.7.13** with the Prisma adapter, email/password auth, and the `admin` + `organization` plugins.

- Server config: `src/lib/auth.ts`; browser client: `src/lib/auth-client.ts`.
- Route handler: `src/app/api/auth/[...all]/route.ts`.
- UI: `/sign-in` and `/sign-up` (`src/components/auth-form.tsx`); session status on the home page.
- After changing plugins or auth config, run `npm run auth:generate`, then `npm run db:migrate`.
- Create the first admin with `npm run auth:create-admin -- --email … --password … --name … --role support`.
- Organization roles and permissions are defined in `src/lib/permissions.ts`; pages and server actions guard with `src/server/auth/actor.ts`. See `docs/permissions.md` and ADR-0011.
- Load the matching skill before config, routes, sessions, plugins, or security work.

- Server/client setup, sessions, plugins: `better-auth-best-practices`.
- Scaffold auth in an app: `create-auth`.
- Rate limits, CSRF, trusted origins, cookies, secrets: `better-auth-security-best-practices`.
- Email verification and password reset: `email-and-password-best-practices`.
- Organizations, members, roles, RBAC: `organization-best-practices`.
- TOTP/OTP, backup codes, trusted devices: `two-factor-authentication-best-practices`.
